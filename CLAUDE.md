# CLAUDE.md

## Project: Two-Stage Recommender with an Honest Evaluation Protocol

A retrieval-plus-ranking recommender built on real impression logs, where **the evaluation
protocol is the deliverable** and the models are the things being measured.

Recommender evaluation is widely broken in three specific ways: random splits leak the future,
sampled-negative metrics can reverse the ranking of methods relative to full-catalog metrics,
and neural models are routinely compared against untuned baselines. This project builds a
two-stage system and then demonstrates, with real numbers, how much each of those three
practices distorts the result.

---

## DECISIONS LOG (these override anything below that disagrees)

Recorded 2026-10-12, after the original spec was written.

1. **Item tower = frozen sentence embeddings (`all-MiniLM-L6-v2`).** Title + abstract are
   encoded once and cached; only the projection/user tower is trained. No language-model
   fine-tuning unless explicitly asked. Adds `sentence-transformers` (approved).
2. **`demo/` web app.** Left: the user's reading history. Right: the recommended feed.
   Toggles on top: (a) sampled-negative vs full-catalog evaluation, (b) random vs temporal
   split, (c) "show what retrieval missed" — a third column with the item the user actually
   clicked that stage 1 never fetched. FastAPI backend over the FAISS index, React frontend.
3. **The demo is built LAST and reads only from `results/`.** Aggregates come from
   `results/metrics.json`; per-user examples come from `results/demo_cases.json`, written by
   `recsys evaluate` from the same run. If something is not in `results/`, it is not on the page.
4. **Every figure is generated by code from `results/metrics.json`** — never by hand, never with
   placeholder data. Four required: method-ranking slopegraph (sampled vs full), retrieval
   ceiling bars, split inflation (temporal vs random), popularity concentration.
5. **item-kNN's grid is declared in `configs/` before any neural model is trained.** It is not a
   strawman; the headline finding may be that it wins.
6. **Build order checkpoint:** Spark ingestion and the evaluation harness are run on
   MIND-small and shown scoring dummy rankings (random, oracle) under both protocols before any
   model is trained (`recsys harness-check`).
7. **Rankers are selected on a later day** (recorded 2026-10-13, after the first multi-seed
   MIND-small run). Train on the `temporal_rtrain` day (2019-11-13), early-stop and choose
   one of the feature sets declared in `configs/` on `temporal_val` (2019-11-14), and refit
   the choice on 2019-11-14. This replaces the same-day user holdout, which a diagnostic
   showed rewarded the GBDT for patterns that did not hold on the next day. The feature sets
   were declared after that diagnostic, which looked at test-day feature distributions and
   test-day ablations. That is disclosed here, and the choice among them is made only on
   2019-11-14.

## HOW TO WORK ON THIS PROJECT (read first)

- **Scaffold the whole codebase in this session**, runnable end to end once the dataset is
  downloaded.
- Build in this order: data and split audit -> evaluation harness -> baselines -> retrieval
  models -> ranking -> findings. **The evaluation harness comes before any model.** If a model
  is built first, the evaluation gets shaped to flatter it.
- **Never report a metric that was not produced by a real run.** No illustrative numbers in the
  README. If something has not been run, say so.
- **Every gate is written down before the numbers are looked at.** See "Pre-stated gates" below.

## THE INVIOLABLE RULE

**No model is evaluated on an interaction it could not have seen at serving time.**

The split is by timestamp, not at random. Train on earlier interactions, test on later ones.
A random split lets the model observe Tuesday while predicting Monday, and it inflates every
metric in this domain.

The random split is still computed, but only as a **comparison artifact**. Both numbers go in
the README side by side, and the gap between them is itself a reported finding.

Second rule, which follows from the first: **a sampled-negative metric is never reported without
the full-catalog number next to it.**

## Data

**MIND (Microsoft News Dataset), large variant.** Roughly 15M impressions, 1M users.

MIND is the right choice specifically because it contains **impression logs** — it records what
was shown to each user, not only what was clicked. Almost every public recommendation dataset
gives positives only, which makes honest negative sampling and position analysis impossible.
News feed ranking is also structurally close to a home-feed problem.

If a larger and messier substrate is wanted later, Amazon Reviews 2023 is the swap. It is bigger
but has no exposure data, which costs you the position and propensity work. Record the reason in
the README if you swap.

**Ingestion and negative sampling run in Spark.** This is not decoration: at this row count the
join and sampling steps are genuinely awkward in pandas, and the pipeline is written to scale
past the sample.

## Architecture

```
raw impression logs
   |
[1] INGEST (Spark)        -> parse impressions, sessions, item metadata
[2] SPLIT + AUDIT         -> temporal split; random split for comparison; leakage checks
[3] EVALUATION HARNESS    -> the deliverable: metrics, protocols, ceilings
[4] RETRIEVAL             -> popularity, item-kNN, two-tower, graph
[5] RANKING               -> GBDT and a neural ranker over retrieved candidates
[6] FINDINGS              -> the four results below, written up honestly
```

### 1. Ingest (`data.py`)
- Spark job: parse impression logs into (user, item, shown, clicked, timestamp) records
- Item side: title and abstract text, category. Keep text, it feeds the two-tower encoder.
- Record row counts, user counts, item counts, and sparsity in `results/dataset_stats.json`

### 2. Split and audit (`splits.py`)
- **Temporal split** by a configured cutoff date. Primary.
- **Random split**. Comparison only, never the headline.
- Audit: assert no test user-item pair appears in train; report cold-start rates (users and items
  unseen in train) for both splits, because that difference is a large part of why random splits
  look better.

### 3. Evaluation harness (`eval/` — this is the project)

**`metrics.py`**
- Recall@k, NDCG@k, MRR, HitRate@k
- Each implemented once and **verified against an independent reference in tests** (a hand-worked
  example, or `sklearn`/`rank_eval` where an equivalent exists). A metric you cannot check is a
  metric you cannot report.

**`protocol.py`**
- Two evaluation modes over the same model and the same test set:
  - **Full catalog**: score every candidate item
  - **Sampled negatives**: score the positive against N sampled negatives (N configurable,
    default 100)
- The harness runs both for every method and emits a paired table.
- **The finding to look for: the ordering of methods under sampled evaluation differs from the
  ordering under full-catalog evaluation.** If it does, that is the headline result.

**`ceiling.py`**
- The ranker cannot recover an item retrieval never returned.
- For each retrieval method, compute the **recall ceiling**: the best score the downstream ranker
  could achieve given the candidate set handed to it.
- Report end-to-end score against that ceiling, so it is visible whether the system is limited by
  retrieval or by ranking.
- This is the most distinctive thing in the repo. Give it its own README section.

**`popularity.py`**
- Decompose each metric into the part explained by item popularity alone
- Report popularity-debiased metrics alongside raw ones

### 4. Retrieval (`retrieval/`)
- `popular.py` — most-popular baseline. Not a strawman; tune the time window.
- `itemknn.py` — item-item co-occurrence with proper normalisation and shrinkage. **Tune this
  seriously.** A large body of published work fails to beat a well-tuned item-kNN, and if that
  happens here it is a result, not an embarrassment.
- `two_tower.py` — user tower and item tower, trained with sampled softmax or BPR. Item tower
  (per decision 1: frozen all-MiniLM-L6-v2 embeddings + trained projection)
  consumes title/abstract text. This is where embeddings come from.
- `graph.py` — LightGCN, or an item co-occurrence graph with propagation. **Cut candidate** if the
  four-week budget is at risk; cut this before cutting anything in `eval/`.

### 5. Ranking (`ranking/`)
- `gbdt.py` — LightGBM over candidate features (retrieval scores, popularity, recency, user and
  item aggregates, text similarity)
- `neural.py` — a simple deep ranker for comparison
- Both are evaluated **only on candidates produced by stage 1**, never on the full catalog. That
  is how the system actually runs, and evaluating otherwise is a lie.

### 6. Serving (`serve/`)
- Build an ANN index (FAISS) over item embeddings
- Report recall against exact search, and p50/p95/p99 query latency
- The point is to show the retrieval/latency tradeoff is understood, not to build a service

## Pre-stated gates

Write these into `GATES.md` **before running anything**, and record pass or fail with the date.
State the gate before the numbers are seen.

- **Gate A** — the temporal split scores lower than the random split for every method. If it does
  not, the split logic is wrong, not the finding.
- **Gate B** — every method is reported under both full-catalog and sampled-negative protocols.
  No exceptions, including baselines.
- **Gate C** — item-kNN is tuned over a declared grid before any neural model is compared to it.
- **Gate D** — the retrieval ceiling is computed before any end-to-end number is reported.

## Conventions

- **Seeded and reproducible.** Seed in config, recorded in `results/metrics.json`. A number that
  cannot be re-run is not evidence.
- Config-driven. No hardcoded split dates, k values, or grids.
- Spark for ingestion and negative sampling. PyTorch for the neural models. Do not quietly
  replace the Spark path with pandas when the sample is small.
- Every metric verified against an independent reference in `tests/`.
- Docstrings state the assumption each metric makes and when it misleads.
- Dependencies: `pyspark`, `pandas`, `numpy`, `scikit-learn`, `lightgbm`, `torch`, `faiss-cpu`,
  `matplotlib`, `pydantic`, `pytest`. Ask before adding more.

## Definition of Done

1. `recsys ingest` runs the Spark pipeline end to end and writes dataset stats.
2. `recsys train` produces all four retrieval methods and both rankers on the temporal split.
3. `recsys evaluate` emits the paired table: every method under both protocols, with the
   retrieval ceiling and popularity decomposition.
4. `results/metrics.json` holds the real numbers with the seed and date recorded.
5. README carries those numbers, the four findings, and a limitations section that names real
   problems rather than hedging.
6. Four figures generated from results/metrics.json: method-ordering slopegraph, retrieval
   ceiling, split inflation, popularity concentration (decision 4).
7. `pytest` passes, including every metric verification.
8. `demo/` serves the three toggles from results/ only (decisions 2-3).

## Shared agent knowledge base

This machine runs an MCP knowledge base ("agent call centre") that other agents write to. The
tools are:

`mcp__callcentre__search`, `mcp__callcentre__get`, `mcp__callcentre__submit`,
`mcp__callcentre__report_outcome`, `mcp__callcentre__open_issue`, `mcp__callcentre__claim_issue`,
`mcp__callcentre__log_attempt`, `mcp__callcentre__resolve_issue`

Use them:

- **`search` first, before spending time on any error** — Spark configuration failures, JVM and
  memory errors, FAISS build problems, cluster job failures. Another agent has likely hit it.
- **`get`** to pull the full write-up of a matching entry.
- **`submit`** when you solve something non-obvious that cost real time, especially Spark tuning,
  OOM fixes, and dataset quirks in MIND.
- **`report_outcome`** after trying a suggested fix, whether or not it worked. A fix that failed
  is useful information.
- **`open_issue`** for a blocker you cannot resolve, with what you tried.
- **`claim_issue`** before working on an open issue so two agents do not duplicate effort.
- **`log_attempt`** while working a claimed issue, so the trail survives if you stop.
- **`resolve_issue`** when it is fixed, with the resolution.

## Why this project exists (keep this framing in the README)

Most recommender work reports a number from a random split, against sampled negatives, versus an
untuned baseline. All three choices inflate the result, and the third can invert the conclusion
entirely. This project builds a working two-stage recommender and then measures what each of those
three shortcuts costs, on the same data, with the same models.
